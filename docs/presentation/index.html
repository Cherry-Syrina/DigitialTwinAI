Happiest Health · Digital Twin Challenge
GlucoTwin AI
A predictive digital twin that turns a glucose sensor stream into personalized, forecast-aware risk monitoring for people with diabetes.
Synthetic data · Demo prototype · Not clinically validated
3-minute pitch — 12 slides · 30/60/90/120-minute glucose forecasts · risk flags
01 · Problem
People act on glucose readings that are already in the past.

Continuous glucose monitors report *today's* value. By the time a person reacts, their glucose has moved on — so decisions are reactive, not preventive.

5 min
sensor cadence
  • Current value is already 5 minutes old
  • Trend arrows are coarse
2–4 h
action lead time
  • Meals/insulin act over hours
  • Need to act *before* a rise or drop
static
thresholds
  • Fixed cut-offs ignore context
  • One-size-fits-all risk advice
The gap: no per-patient "living model" that forecasts the near future and translates it into an actionable risk level.
02 · Idea
A digital twin that is you — updated every 5 minutes.

Build a per-patient state (the twin) that ingests live CGM/wearable data, forecasts glucose at four horizons, and flags risk *before* thresholds are crossed.

Per-patient state
  • Latest sensor window (60 min lookback)
  • Static health profile (age, type, HbA1c, BMI)
  • Meal/sleep/activity context
  • Forecast + risk derived from that state
Forecast-aware risk
  • GBM forecasts at +30/60/90/120 min
  • Signals: glucose, insulin, carbs, steps, HR, sleep
  • Risk level & flags from predicted horizon
  • Exports a consult, non-clinical report
"Not just *where am I now*, but *where am I heading?*"
03 · Architecture
Pipelines, engine, model, API, dashboard.
Synthetic data → validation → digital-twin engine → GBM forecaster → risk service → FastAPI → React dashboard. Training artifacts (joblib + metrics) persist in a model registry.
04 · The twin engine
A patient's state: live, windowed, replays.
State snapshot
  • Replays the sensor stream in 5-min steps
  • Keeps the latest valid 12-row (60 min) window
  • Handles dropped readings gracefully with NaN
  • What-if: mutate carb/insulin/sleep and re-forecast
Demo behaviour
  • /demo/advance steps the twin through time
  • Each step re-computes forecast + risk
  • Full provenance: which rows, which features
  • Interactive "Advance (20 min)" button in the UI
Deterministic, seeded, reproducible — same twin for the same person every run.
05 · Forecasting model
A validation-selected Ridge or GBM per horizon — and honest baselines.
4
horizons
  • +30 · +60 · +90 · +120 min
  • independent, tuned per horizon
  • 30 past-only features, as-of summary data
2
reference baselines
  • persistence (carry-forward)
  • Ridge regression
  • validation-selected GBM or Ridge
70/15/15
time-ordered train/validation/test split
  • train on earliest weeks of series
  • test on the newest
  • no random shuffle — no lookahead
Feature engineering documented in docs/features.md; leakage checks are unit-tested.

07 · Risk assessment
A risk flag the person can act on early.
Configurable thresholds
  • Hypo 70 / critical 54 mg/dL
  • Hyper 180 / critical 250 mg/dL
  • Loaded from JSON — ops-tunable at runtime
  • Risk level: low / medium / high + kind + message
Forecast-driven
  • Score reviews the *predicted horizon*, not just today
  • Flags like hyperglycemia with target time
  • Demo patient GT-003 starts "medium" — visible in-app
  • UI: colour-coded badge + list of flags

09 · Data & trust
Fully synthetic, fully transparent.
Data pipeline (seeded)
  • 8 profiles · 7 days · 16,128 readings @ 5-min
  • EHR-like records + glucose summaries per patient
  • Realistic missing values injected + handled
  • Seed 42 → reproducible datasets
Trust & verification
  • 90 automated backend tests (pytest)
  • "Synthetic tag" badge throughout the UI
  • Non-clinical disclaimer on every page
  • Model metrics and thresholds inspectable in-app
Built for a hackathon proof-of-concept — designed so clinical data could drop in behind the same interface later.
