# GlucoTwin AI

A **predictive digital twin for personalized glucose monitoring** — a full-stack proof-of-concept
built for the *Happiest Health Digital Twin Challenge*.

The system replays a CGM/wearable sensor stream into a per-patient **digital twin**, uses a
**validation-selected Ridge or Gradient-Boosting forecaster** to predict glucose at **+30 / +60 / +90 / +120 minutes**, and turns
those forecasts into **actionable risk flags** before thresholds are crossed — surfaced in a React
dashboard.

> **Synthetic demonstration only.** All data, patients, and model results are generated by this
> repository's deterministic pipeline. Nothing here is a real clinical measurement or a medically
> validated model. Do **not** use this prototype to diagnose or treat anyone.

## 4. How we built it

Two independent-but-joined pipelines share one feature schema:

1. **Training pipeline** (`backend/scripts/train_model.py`) — builds leakage-free features from a
   60-minute lookback window, splits chronologically into **70% train / 15% validation / 15% final test**,
   selects between *Ridge* and *Gradient Boosting* using validation MAE (with persistence as a baseline),
   then refits the selected model on development rows before final test evaluation and persists the artifacts (`models/model_h{30,60,90,120}.joblib`, `models/metrics.json`).
2. **Inference path** (`backend/app/ml/infer.py`) — a `Forecaster` builds the *same features* from
   the twin's current window and returns predictions plus a feature-ablation explanation.

The **twin engine** (`backend/app/services/twin.py`) replays the sensor stream in 5-minute steps,
keeps the latest valid window, and exposes `advance`, `predict`, `what-if`, and `history`.
The **risk service** (`backend/app/services/risk.py`) scores the predicted horizon against
configurable thresholds (`backend/app/data/thresholds.json`) to emit levels and flags.

## 8. How to run locally (Windows / PowerShell)

```powershell
# 1) Backend
py -3.12 -m venv .venv                  # or use python
.\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python -m backend.scripts.generate_data   # regenerates data/synthetic/*
.\.venv\Scripts\python -m backend.scripts.train_model      # regenerates models/*
.\.venv\Scripts\python -m pytest tests                     # 90 backend tests
.\.venv\Scripts\python -m uvicorn backend.app.main:app --reload --port 8000

# 2) Frontend (second terminal)
cd frontend
npm install
npm run dev          # http://localhost:5173  (proxies /api -> :8000)
```

Run everything from the **project root** (Python uses absolute imports); tests, uvicorn, and the
data/model scripts must be started there.

**Doctor workflow (frontend):** Patients → **Add patient** (register) → **Medical Data** (manual
readings, CSV sensor import, EHR records) → **Digital Twin Monitor / Predictions**. New patients and
everything entered about them is stored in a local SQLite overlay (`data/glucotwin.db`; override with
`GLUCOTWIN_DB_PATH`) and survives a backend restart. Open **Reports** to generate, print/PDF or
download the patient report. All entered rows are labelled **DEMO ENTRY** and never mixed with the
synthetic dataset without a provenance label.

### Authentication (opt-in)

Off by default so the local demo runs with zero setup. Set `GLUCOTWIN_AUTH_ENABLED=1` to require a
bearer token on every patient-scoped route (401 without it) and per-patient ownership (403 across
clinicians):

| Method | Path | Description |
|---|---|---|
| POST | `/api/auth/register` | create a clinician account (**`X-Admin-Key` required**, 403 otherwise) |
| POST | `/api/auth/login` | username + password -> bearer token (401 on bad credentials) |
| POST | `/api/auth/logout` | revoke the presented token |
| GET | `/api/auth/me` | identity of the caller |

Passwords are stored as salted PBKDF2-SHA256 digests and tokens as SHA-256 fingerprints - neither can
be recovered from `data/glucotwin.db`. Shared synthetic patients stay readable by every signed-in
clinician; doctor-created patients are visible only to the account that created them. The
demo/front-end UI does not embed credentials - auth is exercised by `tests/test_auth.py`.

Import rules: `ReadingIn` ranges (glucose 10–1000 mg/dL, HR 20–300 bpm, …) are validated per row;
malformed timestamps, duplicates and empty rows are rejected with a reason while the rest of the batch
is still accepted. CSV uploads are parsed server-side (2 MiB / 5000 row limits, BOM-stripped, unknown
columns ignored and reported). Missing values are stored as NULL and **never imputed**.

Interactive API docs: **http://localhost:8000/docs**.

## 10. Model & results (synthetic data only; final temporal test segment)

| Horizon | Selected MAE | Persistence MAE | Selected RMSE | MAE improvement vs persistence | Interval (90%) | Coverage on later test half |
|---|---|---|---|---|---|---|
| +30 min | **4.726** mg/dL | 7.141 | 6.381 | 33.8% | +/-9.80 mg/dL | 88.7% |
| +60 min | **5.114** mg/dL | 11.004 | 6.595 | 53.5% | +/-11.56 mg/dL | 92.9% |
| +90 min | **5.264** mg/dL | 14.234 | 6.805 | 63.0% | +/-11.06 mg/dL | 91.7% |
| +120 min | **5.070** mg/dL | 16.449 | 6.556 | 69.2% | +/-10.77 mg/dL | 90.4% |

- **Selected model:** one validation-selected Ridge or Gradient Boosting model per horizon, scikit-learn pipeline with standard scaling. The selected family is recorded per horizon in `models/metrics.json`.
- **Framework/task:** regression predicting glucose (mg/dL) at +30/+60/+90/+120 min from a 60-minute observation window plus contextual/static features.
- **Synthetic training dataset:** generated by `backend/scripts/generate_data.py` (deterministic synthetic CGM/wearable-like data). No external clinical datasets used.
- **Split methodology:** one chronological 70/15/15 train/validation/final-test split with horizon-sized boundary embargoes (no shuffle). Candidate selection uses validation MAE only; reported model metrics use the later final test segment. Features use only the past lookback window.
- **30 predictive features:** glucose lags (1-12 steps), rolling statistics, slope/delta, steps, HR, sleep, meal context, time-of-day cycles, static profile (age/BMI/years since diagnosis/HbA1c).
- **Baselines:** persistence (current glucose), Ridge regression, and Gradient Boosting are evaluated on the final test segment; model family selection is made from validation results.
- **Uncertainty intervals:** after model selection and refitting on development data, absolute residuals from the final test segment are split chronologically: the earlier half calibrates interval width and the later half measures coverage, separated by a horizon-sized embargo. These are research estimates on synthetic data only; calibration and coverage sets are separate by a horizon-sized embargo, but there is no independent real-world or prospective validation.
- **Limitations:** all metrics and intervals use synthetic data only and do **not** establish clinical accuracy or coverage in real populations. The model is an unvalidated research prototype and **not a medical device**; it must not be used for diagnosis or treatment decisions. The final temporal test segment supports internal technical evaluation only.

## 12. What we are most proud of

- The **twin is a real state machine**: advance → forecast → risk, reproducible and explainable.
- **Honest baselines**: persistence and Ridge are beaten at every horizon, and the gap widens as
  the horizon stretches — exactly where naive methods fail.
- **One feature schema** used by both training and inference reduces train/serve skew.
- **136 passing tests** (90 backend + 46 frontend) including leakage checks, error semantics, CSV
  import rejection, persistence across restarts, and API behaviour.
- **Real physician workflow**: register a patient, enter readings/CSV/EHR, watch the twin update and
  the forecast appear, then export a labelled report — all persisted locally.
- **Synthetic-only claims enforced**: metrics, intervals and UI disclosures are limited to the
  deterministic synthetic dataset; model selection uses a separate temporal validation segment, and
  conformal calibration and coverage are measured on separate chronological portions of the final test segment.

## 14. What would you do differently?

- Replace the 60-minute fixed lookback with a **learned horizon-aware context**.
- Introduce a **causal meal/insulin response model** rather than only autocorrelation features.
- Validate against **real consented CGM cohort** with clinician-defined risk zones from day one.
